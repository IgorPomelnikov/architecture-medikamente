# Стратегия защиты данных — система «Медикаменте»


**Нормативная база (ориентиры):** 152-ФЗ (ПДн), 149-ФЗ, 323-ФЗ (охрана здоровья, врачебная тайна), 63-ФЗ (ЭП/ЭЦП), 187-ФЗ (КИИ — при присвоении статуса), отраслевые требования к МИС и интеграции с ЕГИСЗ/ГосСОПКА.

## 1. Какие данные защищаем

### 1.1. Реестр информационных активов

| ID | Набор данных | Содержание | Контур / хранилище | Субъект |
|----|--------------|------------|--------------------|---------|
| D1 | Анкета пациента | ФИО, ДР, телефон, email, адрес, работа, хронические заболевания | User DB (DMZ), фрагменты в Medicamente DB | Пациент |
| D2 | Визит к врачу | ФИО/год рождения, дата и время приёма | Medicamente DB | Пациент |
| D3 | Исследование | ФИО/год рождения, результаты анализов | Medical DB, Kafka (лаборатория) | Пациент |
| D4 | Медицинская карта | ФИО, год рождения, сведения о здоровье | Medical DB (критический) | Пациент |
| D5 | История болезни | Жалобы, диагнозы | Medical DB (критический) | Пациент |
| D6 | Платёжная информация | Счёт, реквизиты плательщика | Payment API, 1С, Medicamente DB | Пациент / клиника |
| D7 | Данные ТМЦ | Инвентарный номер, состояние, количество | 1С Торговля и склад | Клиника |
| D8 | Учётные данные | Логины, хэши паролей, токены, сессии | Keycloak, AD, Redis | Сотрудники / пациенты |
| D9 | Журналы и метаданные | Аудит, lineage, телеметрия (без ПДн в логах) | SIEM, ELK, Marquez | Система |
| D10 | Обезличенные выгрузки | Агрегаты, псевдонимизированные наборы | S3 (BI), ClickHouse (DWH) | Псевдо-субъект |
| D11 | Интеграционные пакеты | Сообщения лаборатории, отчёты в ЕГИСЗ | Kafka, VPN к N3/ГосСОПКА | Пациент / система |

### 1.2. Классификация по чувствительности

| Уровень | Обозначение | Описание | Наборы данных |
|---------|-------------|----------|---------------|
| **Публичный** | P0 | Разглашение не вредит | Справочники без ПДн, публичные расписания (без ФИО) |
| **Внутренний** | P1 | Коммерческая/операционная тайна клиники | D7 (ТМЦ), служебные настройки |
| **ПДн общие** | P2 | Персональные данные (152-ФЗ) | D1, D2, D6 (частично), D8 |
| **ПДн особые (здоровье)** | P3 | Медицинская тайна, спецкатегория ПДн | D3, D4, D5 |
| **Платёжные / финансовые** | P4 | Повышенные требования PCI/бухучёта | D6, 1С Бухгалтерия, ККМ |

**Правило размещения:** P3 — только **Medical DB** и **API медданных** (критический контур); P2 пациента — **User DB** (DMZ); операционные P2 — **Medicamente DB** (корпоративная сеть); в BI — только **P0/P1** после обезличивания (D10).

### 1.3. Классификация по состоянию данных

| Состояние | Описание | Примеры в «Медикаменте» | Основной риск |
|-----------|----------|-------------------------|---------------|
| **At Rest** (хранение) | Данные на диске, в БД, бэкапах, S3 | Postgres Patroni, ClickHouse, MinIO, бэкапы | Утечка носителя, несанкционированный доступ к СХД |
| **In Transit** (передача) | Сеть между контурами и внешними системами | TLS между сервисами, Kafka, VPN в ГосСОПКА/лабораторию | Перехват, MITM |
| **In Use** (использование) | Обработка в RAM, в приложении, на экране | Backend, обезличиватель, сессии в Redis | Dump памяти, shoulder surfing, избыточные права |

### 1.4. Профиль риска (упрощённая матрица)

Оценка: **Вероятность (1–3) × Влияние (1–3) = Score (1–9)**.

| Набор | Угроза | V | I | Score | Приоритет мер |
|-------|--------|---|---|-------|---------------|
| D4, D5 | Утечка Medical DB | 2 | 3 | **6** | Шифрование at rest, ABAC, аудит, изоляция контура |
| D1 | Компрометация User DB / ЛК | 3 | 2 | **6** | TLS, WAF, MFA, маскирование |
| D3 | Перехват в Kafka (лаборатория) | 2 | 3 | **6** | TLS Kafka, ACL, минимизация полей |
| D6 | Мошенничество / утечка платежей | 2 | 3 | **6** | PCI-scope, токенизация у шлюза |
| D10 | Реидентификация в BI | 2 | 2 | **4** | Обезличивание, контроль выгрузок |
| D7 | Искажение складских данных | 2 | 1 | **2** | RBAC, целостность 1С |

## 2. Меры защиты по состояниям и контурам

### 2.1. Защита при хранении (Data at Rest)

| Контур | Хранилище | Данные | Меры |
|--------|-----------|--------|------|
| DMZ | User DB (Postgres) | P2 | TDE/`pgcrypto` для чувствительных колонок, шифрование томов LUKS/dm-crypt, отдельные ключи в Vault |
| Корпоративная | Medicamente DB | P2 | TDE, теги колонок, pgAudit |
| Критический | Medical DB | P3 | TDE + шифрование бэкапов (AES-256), отдельный KMS/Vault namespace, запрет копий вне контура |
| BI | MinIO (S3), ClickHouse | P0–P1 (обезлич.) | SSE-S3/KMS, bucket policy, отдельные credentials |
| Админ | 1С | P1, P4 | Шифрование СУБД 1С, разграничение РМК/бухгалтерии |
| Все | Бэкапы | P2–P3 | Шифрованные бэкапы, offline-копии, ежемесячный restore-test |

**Ключи:** централизованно **HashiCorp Vault** (корпоративная сеть); ротация по регламенту; доступ к ключам Medical DB — break-glass с аудитом.

### 2.2. Защита при передаче (Data in Transit)

| Участок | Протокол / механизм |
|---------|---------------------|
| Пациент → DMZ (ЛК) | HTTPS TLS 1.2+, HSTS, OIDC Authorization Code + **PKCE** |
| DMZ ↔ корпоративная (BFF/Backend) | mTLS или TLS через HAProxy, внутренний CA |
| Корпоративная ↔ критический (API медданных) | mTLS, allowlist IP/сервисов, без прямого доступа BI |
| Критический → BI (обезличенные выгрузки) | TLS к MinIO, односторонний поток, DLP-проверка объёма/схемы |
| Lab Integration ↔ лаборатория | TLS + VPN при необходимости, подпись сообщений |
| Kafka (DMZ Lab / Integration) | TLS + SASL, ACL по topic, шифрование payload для P3 |
| Внешние (платежи, ЕГИСЗ, ГосСОПКА) | TLS/VPN, квалифицированная ЭП где требуется |
| Админ ↔ 1С | TLS/RDP over VPN, сегментация от DMZ |

**Сеть:** firewall между контурами (как на диаграмме); запрет plaintext (PostgreSQL `ssl=on`, `rejectUnauthorized`).

### 2.3. Защита при использовании (Data in Use)

| Мера | Назначение |
|------|------------|
| **ABAC** (через Keycloak + политики / Apache Ranger у Medical API) | Доступ к P3 по роли, отделению, основанию (приём, экстренный случай) |
| **Токенизация** patient_id | В логах и межсервисных вызовах не передавать ФИО |
| **Маскирование** (Ranger / proxy) | Скрытие полей для ролей без полного доступа |
| **Redis** (сессии) | TLS, шифрование at rest, TTL, без ПДн в значениях сессии |
| **Secure coding** | Запрет ПДн в логах, параметризованные запросы, секреты только из Vault |
| **DLP** (контур почты/экспорта) | Контроль вложений и выгрузок (закрывает проблему из Task 1) |
| **Экран / рабочее место** | Политики для врачебных АРМ (блокировка, запрет локальных копий PHI) |

Полное «шифрование в памяти» (confidential computing) для MVP не обязательно; достаточно минимизации данных в процессе + строгого RBAC/ABAC.

## 3. Базовые инструменты защиты (что добавить в систему)

Инструменты сгруппированы по функциям и привязаны к контурам.

### 3.1. Идентификация и доступ

| Инструмент | Контур | Назначение |
|------------|--------|------------|
| **Keycloak** (внешний + внутренний) | DMZ, корпоративная | SSO, OIDC, PKCE для пациентов; OIDC + federation с AD для сотрудников |
| **Active Directory** | Critical Domain / корпоративная | Учётные записи персонала, группы |
| **Apache Ranger** (или OPA) | Критический, корпоративная | ABAC, маскирование, политики к Medical DB / API |

### 3.2. Шифрование и секреты

| Инструмент | Контур | Назначение |
|------------|--------|------------|
| **HashiCorp Vault** | Корпоративная | Ключи БД, TLS-сертификаты, API-ключи интеграций |
| **Postgres TDE / pgcrypto** | DMZ, корпоративная, критический | At rest |
| **MinIO SSE-KMS** | BI | Шифрование обезличенных объектов |
| **Let's Encrypt / внутренний PKI** | DMZ, периметр | TLS-сертификаты |

### 3.3. Сеть и периметр

| Инструмент | Контур | Назначение |
|------------|--------|------------|
| **Firewall** (аппаратный/NGFW) | Между контурами | Сегментация (уже на схеме) |
| **HAProxy** | DMZ, корпоративная | TLS termination, rate limit |
| **VPN** (к ГосСОПКА, N3) | Критический | Защищённый канал к внешним госсистемам |

### 3.4. Данные и пайплайны

| Инструмент | Контур | Назначение |
|------------|--------|------------|
| **Обезличиватель данных** | Критический (на границе) | Псевдонимизация/обезличивание перед S3 |
| **Apache Airflow** | BI | ETL только из обезличенных источников |
| **Apache Kafka** (TLS) | DMZ Lab, Integration | Очереди без утечки в открытом виде |

### 3.5. Наблюдаемость и реагирование

| Инструмент | Контур | Назначение |
|------------|--------|------------|
| **MaxPatrol SIEM** | Critical Domain | Корреляция событий, интеграция с ГосСОПКА |
| **pgAudit** | Все Postgres | Аудит SQL к ПДн/медданным |
| **ELK / OpenSearch** | Корпоративная | Централизованные логи (без ПДн) |
| **Prometheus + Grafana** | Корпоративная | Метрики доступности, алерты |
| **OpenTelemetry** | Все приложения | Трассировка без чувствительных атрибутов |

### 3.6. Резервное копирование и отказоустойчивость

| Инструмент | Контур | Назначение |
|------------|--------|------------|
| **Patroni** + etcd | Postgres-кластеры | HA БД |
| **pgBackRest / WAL-G** | Все Postgres | Шифрованные бэкапы, PITR |
| **Регламент restore-test** | Организационный | |

## 4. Автоматизированный контроль данных

### 4.1. Цели автоматизации

- обнаружение несанкционированного доступа и аномалий;
- непрерывный аудит операций с P2/P3;
- контроль целостности пайплайнов и выгрузок;
- соответствие политикам (кто, что, когда читал/экспортировал).

### 4.2. Средства контроля

| Средство | Что контролирует | Как работает |
|----------|------------------|--------------|
| **SIEM (MaxPatrol)** | Логины, firewall, IDS, pgAudit, приложения | Правила корреляции, алерты, отчёты в ГосСОПКА |
| **pgAudit + PostgreSQL logging** | SELECT/INSERT/UPDATE/DELETE к P2/P3 | Запись в SIEM/ELK, хранение ≥ 6 мес. (по политике) |
| **Apache Ranger** | Запросы к Medical DB/API | Deny по умолчанию, маскирование, отчёты по политикам |
| **DLP** (на почту/экспорт/USB) | Утечки ФИО, СНИЛС, диагнозов | Сканирование исходящих каналов |
| **OpenLineage + Marquez** | Пайплайны Critical → BI | Пунктирный audit trail: dataset → job → dataset (без значений полей) |
| **Apache Atlas** (опционально, фаза 2) | Каталог активов, классификация тегов | Связка с Ranger |
| **Prometheus alerts** | SLA БД, рост ошибок 401/403, lag Kafka | Оперативное реагирование |
| **Vault audit log** | Обращения к секретам | Расследование компрометации ключей |
| **Airflow SLA/DAG sensors** | Объём выгрузок в S3, схема файлов | Блокировка DAG при отклонении от эталона |
| **SOAR** (фаза 2) | Инциденты из SIEM | Автоизоляция учётки, блок IP |

### 4.3. Схема контроля по контурам

```text
[Приложения] → структурированные логи (без ПДн) → ELK
[Postgres pgAudit] ─────────────────────────────→ SIEM → ГосСОПКА
[Keycloak / HAProxy] ────────────────────────────→ SIEM
[Ranger / Medical API] ──────────────────────────→ SIEM + отчёты ИБ
[Airflow] ── OpenLineage ──→ Marquez (корпоративная)
[DLP] ───────────────────────────────────────────→ SIEM (инциденты)
```

### 4.4. KPI автоматизированного контроля

| KPI | Целевое значение |
|-----|------------------|
| Покрытие аудитом P3-таблиц | 100% |
| Время доставки критичного алерта в SIEM | < 5 мин |
| Успешный ежемесячный тест восстановления бэкапа Medical DB | 100% |
| Доля TLS-трафика между сервисами | 100% |
| Инциденты DLP без разбора | 0 |
